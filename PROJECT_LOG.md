## 2026-08-30 (5) — A disciplined staged-debugging rule, a real structural finding, and one confirmed fix

Rick added a standing rule to `CLAUDE.md` this session (under Communication rules): before touching code on anything with multiple real stages, write out the intended chain in order and test each stage in that order, stopping at the first actual failure — don't jump to the next plausible cause. Prompted directly by this thread: several fixes landed in a row (trailing-slash validation, a card restructure, a mainDocuments revert-then-restore) without the underlying "why doesn't Guild Video's overlay register" question ever actually closing.

Applied that rule for real this round, in order:

- **Stega reaches the API, character for character:** confirmed clean, alone. A guildVideo title's raw API string is 1223 characters against ~32 visible ones, real stega code points present.
- **That string survives into the live DOM, character for character:** confirmed directly against production's actual rendered `<h2>` — 1223 characters, identical length, identical stega code points at the point the visible text ends. `renderVideoCard()`'s `esc()` and the `innerHTML` assignment do not touch it. Not a suspect.
- **A real, measured structural difference, found by direct comparison, not theory:** every page confirmed working by a real click (Porch story, Event) has its tagged heading two ancestor levels from `<body>` — `H1 → DIV.container → SECTION.hero`. Guild Video and Featured Fiction — checked the same way, same result on both — sit four levels down: `H2 → DIV.card → DIV.grid → DIV.container → SECTION`. This project has never had a confirmed-working example of the second shape, only the first. Whether that nesting is *why* detection fails couldn't be proven — the actual scan lives behind a cross-frame wall no tool in this session can see into (traced precisely: the "Documents on this page" panel is fed by a Comlink message scoped to a channel between the site's own iframe and the one frame directly embedding it; a listener installed on the outermost Dashboard window sees real Comlink traffic, just not that channel; the one frame that could see it, `swg-studio.sanity.studio`, no longer serves standalone content — visiting it directly redirects straight back into the Dashboard wrapper).
- **A real, confirmed, independent finding: the Guild Video thumbnail had no `data-sanity` attribute.** Rick's read of Sanity's own docs, not a guess — stega only encodes text; images need a separate, manual attribute to become click-to-edit targets at all. Confirmed directly (`img.hasAttribute('data-sanity')` → `false`) before touching anything. Fixed: `the-work/videos/index.html`'s preview-only card renderer now builds that attribute by hand, in the exact documented format, rather than importing `createDataAttribute()` from `@sanity/visual-editing` — that import would have bundled the package into the page's always-loaded chunk for every visitor, the same mistake already made and reverted once this session with `stegaClean()`. Built locally, full 64-page comparison clean on the test branch and again on production after deploy, attribute confirmed present with real document data in preview mode and confirmed absent for a normal visitor, console clean, rollback is a single commit (`b10fa5a`).
- **A test that looked promising and had to be thrown out, reported honestly rather than stretched into an answer:** tried to isolate whether the *title text* (not the image) is independently clickable, outside Presentation Tool, by patching `window.open` to catch any attempt to hand off to Studio without depending on a real popup. Ran it against Guild Video: nothing. Ran the identical test as a control against the Porch story title — the one confirmed-working page in this whole project, its highlight boxes visible in the very same screenshot — also nothing. The test doesn't discriminate a working page from a non-working one, so it answers nothing about either. Recorded here so a future session doesn't re-invent the same dead end.

**Where this leaves the actual open question:** the thumbnail fix is real, confirmed, and shipped, independent of everything else. Whether the *title* on Guild Video or Featured Fiction actually completes a click-to-edit jump is still exactly where it was — behind a wall only a real click inside a real, authenticated Presentation Tool session can get past. ## 2026-08-30 (3) — The real bug: preview mode never turned on for two of the three pages

Rick tested inside real Presentation Tool (something this session's tools can't reach) and reported Events working correctly, but Guild Video still leaving for YouTube on any click anywhere on the card, and Featured Fiction doing nothing at all when clicked. The (2) entry's card-restructuring fix was real and correctly deployed — confirmed directly by pulling the live production JS and finding the new code in it, byte for byte — but it didn't matter, because of what it was sitting on top of.

**Root cause, found by inspection, not guessed:** `isAllowedRedirectPath()` in `api/preview.js` validates the exact page Presentation Tool is asking to turn preview mode on for. The Porch and Events checks were written as regexes that accept the page path whether or not it ends in a slash. The Featured Fiction and Guild Video checks — added this session — were an exact-string `Set`, requiring the trailing-slash form specifically. If Presentation Tool ever asked for either page without one, the check silently failed and preview mode never activated for that page — a deliberate 404 with no distinguishing detail, by design, so there was nothing for Rick or this session to see going wrong. Everything built earlier in this session for these two types sat downstream of that gate: with preview mode never turning on, the site served the exact same page a normal visitor gets, which is a card fully wrapped in a real YouTube link for Guild Video (matches "any click leaves"), and a page with no stega encoding at all for Featured Fiction (matches "no editing capacity" — nothing to click in the first place).

Fixed by replacing the exact-match `Set` with two regexes shaped exactly like the already-correct Porch/Events ones (`/^\/the-work\/featured\/?$/`, `/^\/the-work\/videos\/?$/`). Verified the corrected logic against every path shape this function handles, both slash forms, plus confirmed it still correctly rejects paths that were never meant to match. Couldn't verify the exact failing Presentation-Tool-issued request itself — that requires a real per-session secret Presentation generates internally, not something reproducible outside an authenticated Studio session.

**A second, independent fix landed alongside this one, kept even after finding the real cause:** a global rule (`js/nav.js`, inside the same `isPreviewing()`-gated block that already loads the visual-editing overlay) that stops any click on a link pointing to a different origin while previewing, site-wide — not just on the cards patched so far. Rick's own framing drove this: "the presentation area has no need to edit or access YouTube" is true of every external link on the site (Buy/Ebook buttons, ticket links, the Porch story's Substack fallback), not just the one that happened to get reported first. This is a backstop, not the fix for today's actual bug — it depends on the same `isPreviewing()` gate the trailing-slash bug was breaking, so it would have been silently inert for these two pages too until the real fix landed.

**Caught mid-course and worth remembering:** this session wrote a card-specific fix, then jumped straight to writing a second, broader fix (the click-blocker) without first confirming the *first* fix had actually taken effect where Rick was testing — confirmed later that it had (production was serving the right code), which meant the click-blocker was solving the wrong layer of the problem. Rick's "have you thought this through" stopped that before it shipped past a branch. The lesson isn't "don't add defense in depth" — the click-blocker is good and stayed — it's "confirm the specific failure before reaching for the next fix," especially when each fix sits behind the same gate as the last.

**Still unverified, same limitation as every entry above:** whether this actually closes it needs Rick, MJ, or Grace clicking inside a real, authenticated Presentation Tool session. Full 64-page comparison re-run clean against live production after this deploy; the security gates (no cookie / forged cookie → 404) re-confirmed on production directly.

## 2026-08-30 (2) — Real bug found after "done": video card titles fell through to YouTube

Rick caught this immediately after the entry above was written: clicking a guild video's title didn't jump to Sanity, it navigated to YouTube. Confirmed directly, not dismissed — this is exactly the class of thing CLAUDE.md's "if he flags a possible cause, check it" rule exists for.

**Root cause, confirmed by direct DOM inspection, not guessed:** `renderVideoCard()` (js/sanity.js) wraps the *entire* card — thumbnail, label, title, description, all of it — in one real `<a href>` pointing at the video's YouTube/Substack URL. The Porch story and event pages never had this problem because their titles were always bare headings with nothing underneath them; nothing to fall through to. The video (and by structure, book) cards are different: `document.elementFromPoint()` at the exact center of the title text returned the bare `<h2>` itself, with no Sanity overlay anywhere in the hit path — so a real click lands on the title, bubbles up through nothing-in-particular, and the browser's native "this is inside a link" behavior wins, taking the visitor to YouTube instead of Sanity ever getting a chance to react.

Checked `featuredFiction`'s `renderBookCard()` too, since it's the other new listing-page type: its title was never wrapped in a link to begin with (only the Buy/Ebook buttons are their own separate anchors at the bottom) — so it doesn't have this failure mode. Only guild video needed the fix.

**Fix, approved by Rick before building:** a preview-only `renderVideoCardPreview()`, page-local to `the-work/videos/index.html`, used only when `isPreviewing()`. Same exact look as the real card, but the link only wraps the thumbnail and the "Watch →" line — the title is a bare heading again, with nothing underneath it to fall through to, matching the Porch/event pattern. A normal visitor still gets the original `renderVideoCard()` from `js/sanity.js`, byte-for-byte unchanged — confirmed directly on the live site after deploy (title still sits inside the real YouTube link for a cookie-less visit, exactly as before). `esc()` and `formatDate()` (`js/sanity.js`) are now exported so the preview-only renderer could reuse them instead of duplicating the logic — both already existed in that file, so exporting them added nothing to the bundle.

**Verified, not assumed:** on the test deployment, a real coordinate-accurate click (computed from the title's actual `getBoundingClientRect()`, not the accessibility tree's sometimes-stale reported position) landed on the title after the fix and produced no navigation and no new tab — the failure mode is now structurally impossible, since there's no link left to fall through to. Re-ran the full 64-page comparison after this fix, both against the test deployment and against live production post-merge: 0 mismatches both times.

**Still the same honest limitation as before:** whether Sanity's overlay itself successfully opens Studio on a real click (the *positive* outcome, not just "doesn't misfire") needs a real click inside an authenticated Presentation Tool session, same as Events/Featured/Video's original build note above.

**Worth remembering:** this whole class of bug — a click-to-edit field that's also the descendant of a real link elsewhere in the app — is exactly the scenario Sanity's own docs cover with `data-sanity-edit-target`/edit groups. Didn't reach for that here since the simpler fix (don't nest the title in the link at all, preview-mode only) fully matched what already works elsewhere on this site. ## 2026-08-29 (2) — Click-to-edit fully working, confirmed live

Closes out the "Open, not done" item from the entry below: after shipping click-to-edit, Rick reproduced Presentation Tool's "Unable to connect" banner for real, on the live site, right after that deploy — the follow-up check this session deliberately deferred to. **Bug 2 — that fix didn't actually clear the banner**, and the reason turned out to be unreachable by every tool available this session: the exact console error lives inside Presentation Tool's own UI, which is a same-origin-looking but actually isolated iframe nested two levels deep (top dashboard → Presentation Tool's own iframe → the site's iframe) — none of Claude Browser's, Claude in Chrome's, or any DevTools-adjacent tool's console/network readers could see into that middle frame, even with a live, reproducible failure sitting right there.
