## 2026-09-06 (later) — Jean-Paul's Tarot, Phases 3-4: both engines built and hardened, first real page live

**Phase 3 — the two engines**, built as one shared serverless function (`api/tarot.js`, dispatched by `?engine=text|image`) rather than two separate files, since the project sits at Vercel's Hobby-plan 12-function ceiling and two new files would have broken the next deploy — same consolidation pattern as `preview-singleton.js`.

Text engine calls Claude (`claude-sonnet-5`) with `tarotVoiceText`'s instructions. Real bug hit and fixed: Sonnet 5 defaults to adaptive thinking, and the first attempt's token budget was entirely consumed by thinking with nothing left for the actual answer — fixed with `output_config: {effort: 'low'}` and more headroom. A real regression then surfaced in testing: readings were naming the literal answer word back (e.g. "that truck's kept better secrets"), violating tarotVoiceText's central rule. Fixed twice — first a stronger prompt-level self-check reminder, then (at Rick's request) a real code-level hard backstop: after each generation, the code itself scans the reading for literal significant words from the three answers and automatically retries (up to 3x) with the specific violating words named back to Claude if any are found, throwing a clear error rather than shipping a bad reading if still unresolved. Confirmed clean on 4 real test sets including a deliberately adversarial one (the answer repeated the forbidden word three times in a row).

Image engine calls Gemini (`gemini-2.5-flash-image`) with `tarotVoiceImage`'s instructions plus the reference image set. Needed a real Google Cloud billing account attached before any image generation worked at all (free tier = zero quota for this model) — Rick connected billing mid-session. Multiple real, confirmed problems found and fixed through live testing, each verified with real before/after images, not assumed:
- A visible off-white matted border slipped through the first (vision-model-only) check — added a second, independent hard backstop that decodes the actual PNG pixels (a small dependency-free decoder using Node's built-in zlib, no library) and rejects any image whose four edges are simultaneously flat-colored and light, which a real edge-to-edge painted scene would essentially never do by coincidence.
- Answers that literally named one of the four fixed reference scenes (esp. "beach") kept colliding with the reference set and getting rejected — added explicit reinterpretation guidance to `tarotVoiceImage` itself (not just the code prompt) for exactly this case.
- Color came back muted/desaturated on passing images — added an explicit saturated-color requirement.
- The Duane Allman test set produced an image with zero trace of that answer — traced (not assumed) by comparing an earlier, less-constrained generation that *did* include a person, against a later one that dropped it as more hard rules got added; points at the model deprioritizing the harder answer under prompt load, not a content-safety refusal, though not provable with certainty from outside. Fixed with an explicit "never drop an answer" instruction, confirmed via a real before/after pair.
- One more real, confirmed root cause (not the first guess): repeated failures on the beach/Buc-ee's set turned out to be the model adding readable neon signage ("MOTEL") to roadside-style scenes generally, brand-named or not — found by adding a temporary debug path to actually look at a rejected image instead of guessing further, then fixed at the source in `tarotVoiceImage`. That temporary debug scaffolding, and the separate temporary `bootstrap-ref` mode used to hand-generate style-reference images, were both removed once no longer needed.

**Known open gap:** only 1 of the 4 fixed reference images (the dinner-table scene) is a real file in `api/_lib/tarot-refs/` — the other 3 (beach, garage, garden) were never finished; that work got interrupted by the Studio incident and then by shipping the demo page. The image engine runs and passes its checks with just the one reference on file, but the "proof of range" the full set is meant to provide is incomplete.

**Phase 4 — the first real page**, `/tarot/`: draws 3 questions from the 81 `tarotQuestion` documents across distinct categories (client-side, via a new `fetchTarotQuestions()` in `js/sanity.js` — no new serverless function needed), collects typed answers, calls both engines with the same input, shows the finished card. ## 2026-09-05 (night) — New product concept, decided: "Jean-Paul's Tarot"

A paid, one-of-one card generator, played completely straight in the Guild's established voice.

**Mechanic, settled:** 12 categories of 6 pre-written questions each (72 total, a real writing project on its own — not yet started). Each session draws 3 categories at random, one question from each. The user's 3 raw answers feed two separate, independent generations — one produces the card's image, one produces its name and reading — neither sees the other's output. The resulting mismatch/tension between image and text is the intended product, not a flaw to reconcile. Deliberately not a fixed 78-card deck — every card is generated fresh, one-of-one, never repeated.

**Technical shape:** a real bank of 72 written questions (needs writing). Image generation via Google's Nano Banana (Gemini image API) — confirmed to have a real, standard developer API, same integration pattern as existing Sanity/Kit keys. Text (card name + reading) generated via an automated Claude call, same underlying skill as tonight's prototype card, run without a live conversation. Payment gate via Stripe once that's connected. Real per-image cost checked: roughly $0.005–$0.05 depending on quality tier — cheap at this scale.

**Not yet started:** writing the 72 questions, obtaining a Nano Banana API key, building the actual generation pipeline, nailing a consistent visual "look" across cards (flagged as the real hard part — style consistency across independent generations takes deliberate iteration, not a first-try guarantee).
